# 指示書の雛形(束ねる側が書き写して使う形)

2026-11-19 に、元サイト(別ジャンルのサイト)の指示書の形を、副業サイトの現行の手順に合わせて取り入れた。手順の正は `docs/pipeline/autonomy/FULL-REWRITE-PROCEDURE.md`、規則の本文は `.claude/agents/writer.md`(ここには写さず、参照だけを書く)。置き場は `サイト運営/記事データ/作成中/`(フルパスで書く)。【】は、そのまま使わず、題材に合わせて書き換える所。

## 1. 依頼者の1通の写し(`_指示_<回>_<日付>.md`)

依頼者の1通の全文を、始める前に `サイト運営/記事データ/作成中/_指示_<回>_<日付>.md` に写す(CLAUDE.md の作業方針)。進捗ファイル `_進捗_<回>_<日付>.md` の作り方は `FULL-REWRITE-PROCEDURE.md` の「まとめて直す回」の3。要約だけを写してよいのは、全文が長く、別の所に保存してあるときだけ(その場合は「全文は依頼者の貼り付け」と先頭に書き、他人の投稿の原文・声は写さない)。

依頼者の1通に、次の事柄が書かれていないときは、束ねる側が補って(決めた内容と理由を報告に書く)、共通の守ること(下の2)に入れる。

```
# 依頼者の1通(写し): <題>(<日付>)
<何を作る/直すか>。受け取りたいのは<完成の水準>だけです。「完了条件」をすべて満たすまで、自分で調査・修正・再検査してください。【依頼者は不在。質問しない。迷う点は、依頼者の1通と今の規則の考え方で自分で決め、決めた内容と理由を報告に書く】
依頼者の方針: 担当は<N>体まで並列(基本は20体)。声を集める担当は同時に5体まで。
## 最優先の原則 …(②をずらさない・安全の指示を弱めない・検査を通すためだけの部品や文を足さない)
## 0. 守ること(触らないもの・commit/push・原文を出さない・作業場所)
## 1. 対象の指定(記事ごとに、②の型と②〔読者の悩み、または知りたいこと〕、企画書の場所、他記事との境目)
## 2. 作業の流れ(企画→声[悩み型だけ]→本文→図→画像→確認→直し→検査→回帰チェック。確認・検査・判定は、書いた担当と別の新しい担当)
## 3. 完了条件(番号つき。「字数は目標にしない」「水増ししない」を含める)
## 4. 報告・止まる所
```

止まってよい場合は、`publisher.md` の「保留にしてよい範囲」の3つだけ(声が取れない・声ゼロのときも止めない。2026-11-20 依頼者の決定。`run-article-production/SKILL.md`「企画の前の声の探索」)。止まるときも、保留にするのは該当の記事だけで、残りは進める。依頼者がいる回は、判断が要る点を「依頼者に聞くこと」として報告に書く。

**目視(2026-11-20 依頼者の回答)**: 依頼者は、書き直した記事を基本的に目視する。1通に目視の順(公開の前か、あとか)が書かれていれば、そのとおりにする。書かれていない回は、現行どおり、本文を直していない担当の判定を通したものを公開し、依頼者の目視は公開のあとにする。目視用の資料は、報告にフルパスで書く(`FULL-REWRITE-PROCEDURE.md` の手順3・4)。

## 2. 共通の守ること(`_共通の守ること_<回>.md`。担当の起動の指示は、これを最初に読ませる)

必ず入れること(11項目)。

1. **日付とパス**: 回の日付。サイト運営・サイト本体・作成中の記事フォルダのフルパス。
2. **今回が何をする回か**(下書きを作る回/確認する回)と、**してはいけないこと**: 公開・置き換え・リンクの付け替え・commit・push・fetch・pull をしない。git は読み取り(status・diff・log・show)だけ。add・commit・push・checkout・reset・stash・--no-verify は使わない。
3. **触ってよいもの**(自分の担当フォルダの新規ファイル、または指定の下書き1本だけ)と、**触らないもの**(他の下書き、公開済み・公開待ち、規則本文、検査のスクリプト、サイトのコード、スキル、開発サーバー)。
4. **変えないもの**(②=記事の問い、題・slug・date、安全の指示、大見出しの数と順、既存の図・出典の記法など)と、新しい方法・数字・出典を足さないこと。
5. **最優先の原則**(②をずらさない・安全の指示を弱めない・出典を新しく探しに行かない・数字や収入・税・投資の断定を作らない・検査を通すためだけの移動や追加をしない)。
6. **直す前の写し**を `<元の名前>_第N回前.md` で同じフォルダに残す。直し前後を `直し前後_第N回.md` に書く(前後の文・理由)。回をまたいだ巻き戻しができる。
7. **検査の走らせ方**: `verify-article.js` は標準出力だけを読む(担当は、検査結果のJSONを `docs/pipeline/verify/` に保存しない。保存は束ねる側が `publisher.md` の手順で行う)。他の担当の結果を上書きしない。走らせ方は `writer.md` の「検査の走らせ方」。
8. **書き込みは LF のまま**(CRLF にしない)。
9. **質問しない**: 依頼者がいる回でも、最も妥当な読みで進め、読みの内容を報告に書く。決められない点は直さず、一覧にして報告する。
10. **出力の場所と報告の型**: 内容はファイルに書き、完了の報告は3行以内の要点だけ(中身はファイルに)。パスはフルパス。他人の投稿の原文・アカウント名・URLを出さない。事実・推測・未確認を分ける。工程ごとに担当フォルダへ保存する(途中で止まっても再開できる)。
11. **規則の参照**: 規則の本文は1か所(`writer.md`)だけが正。指示書には写さず、参照だけを書く。`verify-article.js` は、止める項目が全てPassになるまで直す。

あわせて毎回入れること。変えないものの列挙(公開済み・公開待ち・規則本文・設定・既に完成した記事のフォルダ)/ 作業場所のルール(作成中の下に、記事のフォルダと回のフォルダ以外を増やさない)/ 声の原文・アカウント・URL・IDを報告にも原文なしのファイルにも出さない / 件数・頻度を優先の理由にしない / 変更前の写しを新しい名前で残す / **悩み型でない記事(知りたいこと型)に、悩みを作らない(声の探索・ヒアリングの節・「困っていませんか」を足さない)**。

## 3. 担当の起動の指示(1担当 = 次の4点だけ)

「あなたは<役割>。先に<共通の守ること>と<依頼者の1通>を全文読み、従う」+「対象フォルダ・旧版・声(悩み型だけ)」+「出力(ファイル名)」+「報告は要点3行以内」。役割ごとの差は次のとおり。

- **声(voice)。悩み型の記事だけ**: `voice-researcher.md` と規則34に従い、記事は書かない。出力は `voices.md`(原文のまま・匿名・区分と理由1行・取れなかったソース。全ソースで1件も取れなければ「声ゼロ」と書く〔保留にしない。記事は進める。2026-11-20〕)。答えの語は検索語に入れない。作文・要約・想像は禁止。最後に「声から見える問い」を、旧版の問いと比べて1〜2行。**知りたいこと型の記事には、この担当を起動しない。**
- **書く(write)**: 企画書(`meta.md`)の最初に、②の型(悩み型/知りたいこと型)と理由を書く。悩み型は声に基づいて、知りたいこと型は検索する言葉と題材から、②を1文で書く(知りたいこと型は、悩みに言い換えない)。構成は規則35(i-1)の型の流れ(悩み型: ヒアリング→原因→続けるとどうなるか→答え→締め。知りたいこと型: 前提→答え→締め)。出力は記事ファイルと `書き直しの報告.md`(「図にしたい候補」・字数)。字数は目標にしない。増やすのは深掘りで、水増しはしない(規則33(c)・35(h))。
- **図(fig。本文を書く担当が兼ねてよい)**: 図の指示(規則28)を読み、旧版の図が②に合えば使い、足りなければ新しい図を作る。描画検査の約束(文字を線・図形に重ねない・幅320/375/768pxで確かめる・矢印を文字の上に通さない・文字は小さくしすぎない・注記は短く)。自分の目で画面を確かめ、`図の記録.md` に書く。
- **確認(check。別の新しい担当)**: 書き手・図の報告を読まず、旧版・下書き・声(悩み型だけ)・図の記録だけを渡す。判定の項目は次のとおり。**②が、悩み型は「真の悩みか・真に解決しているか・読者が求めている内容か」、知りたいこと型は「読者が知りたいことか・知りたいことに答えているか・読者が求めている内容か」**(質の定義は元サイトの依頼者の決定。AIが質の良し悪しを決めない。「かもしれません」が多いのは問題にしない。問題にするのは、「〜と思います」のような書き手の決めつけと、だらだらした列挙)/ ②のずれ / 安全の指示・出典・消えた内容 / 規則35(a)〜(f)の違反 / 絵文字 / 深掘り(字数で測らない)/ 図(画面で見る)/ 知りたいこと型に悩みが作られていないか。出力は `確認の記録.md` の1ファイルで、最後に「直すべき点」を高・中・低で書く。下書きは直さない。
- **直し(fix。書き手・図・確認でもない新しい担当)**: 確認の高と中を反映し(低は妥当なものだけ)、直したあと `verify-article.js` を走らせて止める項目がPassになることを確かめる。直しの記録に「直した点・直さなかった点と理由・検査結果・最終字数」を書く。最後に、下書きを目視用の場所(`FULL-REWRITE-PROCEDURE.md` の手順3)へコピーする。
- **深掘りの書き・確認(字数に頼らず、答えが浅い記事用)**: ②・題名の約束・既存の図は変えず、答えを深く掘る(つまずく場面の分岐・自分の場合の判断の基準・うまくいかなかったときの戻り先・見落としやすい点とその確かめ方)で増やす。同じことの言い換え、読者が言われなくてもすることの書き足しは禁止。新しい事実は一次情報で確かめて出典欄に足す。

担当の段の順は、**悩み型**が「声 → 書く → 図 → 確認 → 直し」、**知りたいこと型**が「書く → 図 → 確認 → 直し」(声の段を省く)。同じ組の記事は並列、1記事の中の段は直列。公開・置き換え・commit・push・検査結果の保存は、担当の段に含めず、束ねる側が行う。
