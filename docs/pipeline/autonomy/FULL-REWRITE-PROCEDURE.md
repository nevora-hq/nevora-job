# 全記事見直し(企画からの全面書き直し)の手順

- 手順は `作成中/_指示_*.md`・`作成中/_報告_*.md` に断片的に残さず、本ファイルを正本とする。「作成中/」は `サイト運営/記事データ/作成中/` を指す。報告に書くパスはフルパスにする(CLAUDE.md の作業方針)。
- 記事の置き場(作成中・公開待ち・公開済み。2026-10-12)の決まりは、`.claude/skills/run-article-production/SKILL.md` の「記事の状態と置き場」が正。この手順の記事の作り直しも、作成中に作業用のフォルダを作り、できた版で公開済みの同じファイルを置き換える。
- このサイトの期は、すべて運用期である(2026-10-10 の依頼者の決定。設計期はない)。
- **多層判定(`run-local.js`の第1〜6層・self-test)は経ない。** 最終判定は依頼者の目視。**依頼者は、書き直した記事を基本的に目視する**(2026-11-20 依頼者の回答)。目視の順(公開の前か、あとか)は、依頼の1通に書かれたとおりにする。指定が無い回は、現行どおり公開のあとに目視する(下の「公開と目視の順」)。依頼者が不在の回は、本文を直していない担当の判定に置き換える。理由: run-local.jsのself-testは意図的に停止中である(`docs/pipeline/autonomy/SELFTEST-PAUSE.md`参照)。全記事見直し・ルール改修の期間は、この経路を使わない運用にしている。
- 2026-11-19 に、元サイト(別ジャンルのサイト)で確定した手順を、このサイトの現行の手順に合わせて取り入れた。**規則の本文(語尾・フック・図の型など)はここに写さない。** 記事の書き方は `.claude/agents/writer.md`、公開は `.claude/agents/publisher.md`、担当への指示の書き方は `docs/pipeline/autonomy/指示書の雛形.md` が正。ここには「何を、どの順で、誰が、どこに置いて、どう確かめるか」だけを書く。

## 0. 共通の前提(どの工程にも当てはまる)

- **体制と禁止**: 担当(サブエージェント)は、ファイルを直して「変更したファイルの一覧」を報告するまで。commit・push をしない(してよいのは公開の手順を実行する束ねる側だけ。`publisher.md` の「commit・pushをしてよい者」)。担当への指示にも「commit・pushしない」を書く。
- **成果物の置き場**: 調査メモ・集計・提案・報告・指示の写し・画像のプロンプト・一時ファイルは、`作成中/` の下だけに置く(記事ごとのフォルダ、または回のフォルダ `作成中/<日付>_<回の名前>/`)。`docs/` とリポジトリ直下には置かない。`docs/` に置くのは、規則・恒久の手順書と、公開の手順が決めた記録(検査結果の保存など)だけ。作成中は git の追跡外なので、他人の投稿の原文(声)を置いてもリポジトリに入らない。
- **他人の投稿の原文・アカウント名・URL・投稿IDは、報告にも原文なしのファイル(企画書・まとめ・一覧)にも出さない。** 声は番号だけで示し、原文は `voices.md` だけに置く(`writer.md` 規則34)。
- **件数・頻度を、優先の理由にしない**(「検索が多いから」「声が多いから」で決めない)。
- **「確認済み」と書くのは、取得して確かめた項目だけ。** 調べの報告は、事実(読んで確かめた)・推測(読みからの判断)・未確認(読んでいない)に分けて書く。読んでいない記事・範囲について書かない。件数は、足して合うことを確かめてから書く。
- **着手前**: `git log` の直近を見て、同じファイル・機能に別の作業者の変更が入っていないかを確かめる(重複していたら既存の実装を優先し、報告に書く)。`git status` で未 commit の変更を確かめ、報告に書く。同じ値・同じ変更を多数のファイルへ機械的に当てる前に、対象リストの根拠を明示し、サンプルを確認する。
- **記事に付ける日付・URL**: 既存記事を書き直して置き換えるとき、ファイル名(=slug=URL)・`date`(公開日)は変えない。`updatedDate` は、読者にとって意味のある修正をしたときだけ、置き換えの直前に当日の日付(`"YYYY-MM-DD"`、時刻なし)にする(`date` 以降にする)。誤字・表記ゆれだけの修正に付けない。**公開待ちの記事を書き直すときは `updatedDate` を付けない**(公開処理が `date` を書き換えるため。`.claude/skills/ライター/web-article-writing/SKILL.md`)。
- 題・説明文の語(使わない語・答えを題に書かない・数のフック)は `writer.md` の依頼者の決定が正。迷えば報告に出し、依頼者が決める。
- 出典が弱い主張は、言い切らず、書かないか弱める。出典を新しく探しに行くかは依頼者が決める(`writer.md` の出典の決まり。差し戻し・書き直しの回は、原則、探しに行かない)。
- 公開済みの記事を非公開にする判断は依頼者の決裁(`publisher.md`。不在の回は実行せず、その記事だけ保留)。似た記事の集約・消去は、依頼者が指示したときだけ、下の「集約・消去(依頼者が指示したときの手順)」で行う。勝手に始めない・方式を決めない。

## 1. 並列運用(担当の起動)

- 同時に動かす担当は、対象の記事の数だけ。基本は20体(10体×2組)。多くの記事をまとめて直す回は、20本ずつの組に分けて進める(CLAUDE.md の作業方針。下の「まとめて直す回」)。
- 依頼者が「並列」と書いたときは、実際に並列で起動する(「未確認だから直列」にしない)。段階を踏む場合だけ、最初の3〜4体で型を確かめ、問題なければ20体にする。
- **声を集める担当(voice-researcher。ブラウザを使う)は、同時に5体まで**にする(元サイトで10体を同時に動かしたとき、他の担当の検索結果が混ざる乱れが出たため。このサイトでの実測はまだ無い)。ブラウザを使わない担当は20体まで。実際に同時に走る数は、環境の上限で頭打ちになることがある(起動した数と同時に走った数を、報告で混同しない)。
- **1記事1体。書き手と確認担当は別の新しい担当**(書いた担当は自分の確認をしない)。確認担当には、書き手の報告(書き直しの報告)を読ませない(説明に引きずられないため)。渡すのは、旧版・下書き・(悩み型は)`voices.md`・図の記録だけ。
- **共通の指示を先に渡す。** 共通の指示ファイルを作成中に作り、各担当の起動の指示は「そのファイルを最初に読め」と「割り当て1つ」だけにする(書き方は `指示書の雛形.md`)。
- **巡数の上限を、最初に決めて指示書に書く**(決めないと終わらない)。目安は、直しと再確認で最大2巡(`writer.md` 規則35(i-7)。体数・巡数は参考で、合否に使わない)。上限に達しても残る指摘は、本物の誤り(目的語の抜け・決めつけ・事実の食い違い)なら直し、好みや言い換えの指摘は直さず、一覧にして報告する。
- **終わり方の定義を先に置く。** 例(完了=依頼者の目視待ち): (i) ②のずれが無い(新しい担当が旧版と新版から②を1文で書き、同じと判定。悩み型は「悩み」、知りたいこと型は「知りたいこと」) (ii) 規則違反の指摘が、本物の誤りとして残っていない (iii) 題・URL末尾の名前・日付が旧版と一致 (iv) `verify-article.js` の止める項目が全てPass (v) 目視用でページが開く(HTTP 200)・画像欠けが無い・直した文が入っている (vi) 判断が要る点が、依頼者に聞くこととして表に載っている。区分は「完了(目視待ち)」「指摘付きで目視可(上限に達しても高・中の指摘が残るが、目視できる)」「中止(悪化が戻せない)」。区分ごとの理由を判定の記録に書く。確認の回数が定義より少なかったときは、弱めた点として正直に書く。**直した後の再確認が無い記事は、完了にしない**(未完)。
- 担当の起動リストを、確認の指示に番号で書く(起動し忘れを防ぐ。起動した担当の数と定義の数が違えば、判定に正直に書く)。

## 2. 調べの回(読むだけ。規則・検査・手順を実記事に当てて確かめる回)

1. 目的: 規則・検査・手順を決めるために、実記事に当てて確かめ、結果を作業記録に残す。**実行(公開・置き換え・消去)と調べ(読むだけ)を分ける。** 調べの回は、報告の先頭に「何も実行していない」と書く。
2. 回の始め: 依頼者の1通の全文を `作成中/_指示_<回>_<日付>.md` に写す(CLAUDE.md)。進捗ファイル `作成中/_進捗_<回>_<日付>.md` を作る(下の「まとめて直す回」の3)。共通の指示を作り、前回の訂正があれば先頭に書く。
3. 担当を並列で起動する。担当は自分の出力ファイルだけを書く。親が出力を集め、要約の表を作る。依頼者が目視する資料は、報告にフルパスで書く。**古い目視用ファイルを開く事故を防ぐ**ため、目視用は新しい名前で出し、前のものは書き換えない(変更の案内に、前回との差分だけを書く)。
4. **1回で、1つの規則(または1つの観点)を、10〜13本ほどの記事に当てる。** 複数の規則を一度に当てると、どの直しが改善か分からなくなる。
5. 依頼者の目視を最終の判定にし、機械の検査(`verify-article.js` など)は「悪化していないか」を見る役にする。
6. 依頼者の発言は、日付つきで該当の規則の本文に書く(`writer.md` 規則35(j))。依頼者の発言にない案(設計役の整理)は、決定として書かず、「案」「参考」と明記する。判定の合否が変わる変更は、報告の最初に変更前後の挙動を書く。
7. 依頼者がOKした導入文(フック)を、依頼者の許可なく変えるかどうかは、依頼者に確認する(元サイトでは「OKしたフックは固定」だった。このサイトの扱いは未決)。
8. **同じ検索意図の記事の洗い出し**(調べの回の一種。集約・消去は実行しない): 公開済み・公開待ち・直し中の記事どうしを、今のサイトの題・見出し・本文で比べ、「同じ主要な悩み(悩み型でない記事は、同じ知りたいこと)=同じ検索意図」に答える組を探す。話題が同じだけでは組にしない。判定は、前の判定を見ていない新しい2体が互いの結果を見ずに独立に行い、一致した組だけをグループにする(割れたものは新規扱い。迷うものは「要判断」)。本文を読んで確かめた組と、題・見出しだけで読んだ組を分けて書く。結果は作成中に保存し、依頼者に渡す。集約・分け直し・消去は、依頼者が目視して決めるまで進めない(`writer.md` 規則11(0)「同じ答えを渡している記事」が、1本ずつの書き分けの正)。

## 3. 手順(既存記事の書き直し)

1. **対象の選定**: 書き直す記事の一覧を `作成中/_対象_第N回_YYYY-MM-DD.md` に作る(選定理由・件数を明記)。既存記事を書き直すときは、まだ書き直していない記事から選ぶ(CLAUDE.md)。
2. **書き直し**(1記事1体。ファイル名・`date`・`category`・URLは元のまま変えない。順序の正は `writer.md` 規則35(i-7)の「書き直しの手順」。ここには、その順序に加えて決めておくことだけを書く)。
   - **(a) 企画書(`meta.md`)の最初に、②の型を決める(`writer.md` 規則11(0))。** 書き直し前の記事が悩みの形で書かれていても、型は読者が何を入口にするかで決め直す(迷ったら、②を読者が友人にそのまま言う言葉にして、「〜で困っている」か「〜を知りたい・〜したい」かで決める)。決めた型と理由を1行、`meta.md` に書く。
     - **悩み型**: 企画の前に、可能な限り、声を集める担当(`.claude/agents/voice-researcher.md`)が、記事ごとの `voices.md`(原文・匿名・区分と理由1行)を作る(声は必須でない。2026-11-20 依頼者の決定)。取れなかったソースは、取れなかったと書く。Chromeの拡張が使えないときは、WebSearch・WebFetch で公開ページの声を探してよい。声は、問いの見つけ直し・見出しや導入の言い回し・導入の共感にだけ使い、出典・根拠・数字の裏付けにしない。親は `voices.md` の全文を読む。②の根拠は、区分「悩み」の声の番号だけを書く(`writer.md` 規則11(1)・34)。別枠の声は、別の行に「同じ場面の確認(別枠。根拠ではない): #…」と番号だけを書く。②に近い声の選び方(適合判定)は、区分「悩み」の声を、別々の新しい2体が②に対して「直接適合・部分適合・不適合」で判定し(割れは部分適合)、問いの根拠には直接適合の番号だけを置く。直接適合が少ない(元サイトの目安は3件未満。参考)ときは、企画書の先頭に「根拠不足」と書く。件数の少なさで止めない・「多くの人が悩んでいる」と書かない(規則34)。声が見つからない・取得できない・声ゼロのときも**保留にしない**。声を作文せず、記事は進め、声が無いことを企画書に1行書く(`run-article-production/SKILL.md`「企画の前の声の探索」)。
     - **知りたいこと型(悩みを入口にしない記事。制度・手続きの解説、比較、手順・やり方、用語の整理、最新情報など)**: ②は「読者が知りたいこと・達成したいこと」を、読者の言葉の1文で書く。**悩みを作らない**(「困っていませんか」の問いかけ・題材を正当化するための場面・ヒアリングの節を足さない)。**声の探索をしない**(任意。`voices.md` を作らない。声が無いことを理由に止めない)。②の根拠は、検索する言葉と題材から書く。書き直し前の本文にあった悩みの文は、②に写さず、知りたいことに読み替える。構成は、前提→答え(読者の状況別)→締め、導入は知りたい・やりたい場面から入る(規則35(i-1)・(f))。確認の問い(規則11(0)の(a)「題材を正当化するために作った場面ではないか」(b)「②は読者が友人にそのまま話す言葉か」)を、企画書に答えとして書く。
   - **(b) 落とさない中身の書き写し**: 現在の本文から、依頼者の入力(決めた手順・言い回し・図のラベルの趣旨)と、安全のための指示(怪しい勧誘の相談先・税務の確認先〔規則24〕・収入の断定を避ける言い回し)を、企画書の「落とさない中身」の欄に写してから構成を設計する(規則11(0))。
   - **(c) 図・画像**: 図解は記事ごとに、その記事の②に合うものを置く(規則28。図の要素の本数は規則28(g)で、参考。満たせなくても止めない。満たせない要素は①理由②デメリットを報告し、無理に足さない。steps は図解に数えない。新しい図解の型は作らない)。画像は、置ける見出しへ移す(パスと alt は変えない。`image-placer.md`)。
   - **(d) 通読・文脈読み・直し・再確認**: 新しい担当が全文を通読し、直した文は直す前と並べて、別の新しい担当が前後の文とセットで文脈読みする(規則35(i-7)。**悩み型でない記事の通読は、「悩みを作っていないか」も見る**)。指摘は文脈で1つずつ見て直し、別の新しい担当が同じ文を再確認する。
   - **(e) 検査**: `verify-article.js`(地の文400字連続の確認を含む)で、止める項目をPassにする(走らせ方は `writer.md` の「検査の走らせ方」。結果は標準出力で読み、担当は検査結果をファイルに保存しない。保存は束ねる側が `publisher.md` の手順で行う)。
   - **(f) 回帰チェック**: 落とさない中身・安全の指示・依頼者の方針が本文に残っているかを、新しい担当が全文を読んで確かめる。
   - 組ごとの終わりに「規則35の確認」を行う(書き手とは別の新しい担当が、文脈で1文ずつ読む監査と、軸と深さの監査〔規則35(g)・(h)〕。図の要素の本数〔規則28(g)〕とフックの見せ方〔規則35(f)〕を数える)。数は参考表示で、止めるのは、`verify-article.js` の止める項目と、文単位・軸と深さの本物の誤りの指摘だけ。
3. **目視用ページ(依頼者が見る)**: 依頼者がいる回は、下書きを `サイト運営/サイト本体/content/articles/<slug>_目視.md` にコピーし(`content/` は git の追跡外。`npm run dev` や `npm run build` の前処理 `sync-content.js` が空にして公開済みから入れ直すため、**開発サーバーを起動してからコピーする**。起動のたびに消える)、開発サーバーで `/posts/<slug>_目視` を開く(コードの読みでは、`lib/posts.js` が `content/articles` を読むため表示できるはず。実際の表示は、最初の回に確かめる)。目視用の一覧(URL・HTTP 200・画像欠けの実測)と目視ガイド(どこを開く・何を見る・はい/いいえ)を、報告に付ける。画面写しは親が自分で開いて見る(担当の報告だけで済ませない)。
4. **公開と目視の順**: 依頼者は書き直した記事を基本的に目視する(2026-11-20 依頼者の回答)。目視の順は、依頼の1通に書かれたとおりにする。**指定が無い回は、現行どおり、本文を直していない担当の判定を通ったものを公開し、依頼者の目視は公開のあとにする**(2026-10-03 の依頼者の決定に従う。この決定は、台帳の代行記録をしていた間のものだった。台帳を使わなくなった2026-10-12 以後の扱いは、順が未指定のまま「現行どおり」と読む)。依頼者が、公開の前に目視すると指定した回は、可の出た記事だけを、次の5へ進める(公開の単位=可の出た本数)。
5. **公開済みの置き換えと、項目35の確認(2026-09-28追加)**: 可となった(または判定を通った)版で、公開済みの同じファイルを置き換える(旧版の写しを作成中に残す)。置き換えた記事のうち、図解(`charts`)を新規作成・変更した記事、またはfrontmatter(`heroImage`・`thumbnail`等)を書き換えた記事は、commit する前に、手元で `npm run build`(`サイト運営/サイト本体`)を実行したうえで、対象記事へ `node scripts/verify-rendered-layout.js --strict <slug>` を実行し、検出0件を確認する(`next build` は `公開済み/` だけを取り込むため、置き換えたあとでないと対象が出ない)。0件でない記事は、その記事だけ差し戻して直すか、依頼者に報告して指示を仰ぐ(不在の回は、その記事だけ保留。検出が残ったままpushしない)。
   - この確認が無いと、書き直しで失われた既存の項目35対応(座標調整済み図解・短いラベル・heroImage分離)が、週次実行(item35-weekly)まで気づかれない。
6. **commit・push**: 記事データの変更を、公開の手順(`.claude/agents/publisher.md` の「公開前の必須確認」「commitとpushの単位」)で commit し、pushする。公開ゲート・台帳は、このサイトでは使わない(`publisher.md`)。commit のメッセージに、題・本数・`updatedDate`・「公開日・slug・サムネイルは公開済みのまま」を書く。**公開待ちの記事を直したときは、公開待ちのファイルを直し(公開済みへ移さない)、`publishAt` が残っていることを確かめる**。公開待ちの記事・本文画像は、commit・pushしないと公開キューに届かない。
7. **push後の確認**: push から最低5分待ち、Vercelのデプロイ成功を確認する。成功の条件は CLAUDE.md のデプロイ運用ルールが正(トップページHTTP 200・sitemap の記事URL件数・その組の記事ページHTTP 200。ビルドIDの変化は、サイト本体に変更がある push でだけ条件に含める)。記事数が減っていたら、次の組へ進まず原因を直す。本番のURLは `https://<サイト>/posts/<slug>` のフルで依頼者に渡す(「ある悩みの記事」のような曖昧な指定は、記事・悩みページ・カテゴリページのどれかを誤解させる)。画面の見え方は取得では確かめられないので、親が画面写しを自分で開いて見る。

## まとめて直す回(組ごと)(2026-10-07)

多くの記事をまとめて直す回の進め方。上の手順の依頼者の目視(3・4)は、依頼者が不在の回は、本文を直していない担当の判定に置き換える(CLAUDE.md の「依頼者が不在の回」)。公開の手順の正は `.claude/agents/publisher.md` で、ここには書き写さない。

1. **20本ずつの組に分ける**。組の中の担当の並べ方は CLAUDE.md の作業方針(基本は20体)。
2. **組ごとに、次の順で行う**: 担当が直す → 検査(`verify-article.js` など。走らせ方は writer.md の「検査の走らせ方」)→ 本文を直していない担当の判定(No がなくなるまで。`docs/pipeline/JUDGE-ITEMS.md`)→ 公開(`publisher.md` の「公開の決まり」。pushは組ごとに1回。push の前に `git fetch` で、公開キューの自動 commit〔origin の先行 commit〕が無いかを確かめ、あれば merge で取り込む)→ 本番の確認(push から5分待ち、トップ・記事数・その組の記事を確かめる。記事数が減っていたら、次の組へ進まず原因を直す)。
3. **指示の写しと再開の手順**: 依頼者の1通の全文を `サイト運営/記事データ/作成中/_指示_<回>_<日付>.md` に写す。進捗ファイル `サイト運営/記事データ/作成中/_進捗_<回>_<日付>.md` を作り、先頭に再開の手順(「コンパクトのあと、または再開のときは、_指示_<回>_<日付>.md とこのファイルを読み直し、git status で commit していない変更が無いかを確かめ、下の『次の手順』から、止まらずに続ける。」。依頼者が不在の回は「依頼者は不在。質問しない。」を足す)を置いて消さない。その下に「次の手順」を1行で書き、手順が1つ進むたびに書き直す。会話が切れても、この2つのファイルだけで再開できるようにする。
4. **個別の小さな直し**は、組の作業に混ぜず、先に1つの commit で出す。
5. **変えていない記事**は、公開の対象にしない(`公開済み/` のファイルを変えた記事と、リンク表示だけ直した他記事だけを commit に入れる)。

## 集約・消去(依頼者が指示したときの手順。2026-11-20 元サイトの工程Cを取り入れた)

同じ検索意図の記事が複数あるとき、似た記事を1本に集約(吸収)する手順。**依頼者が指示したときだけ行う。** 洗い出し(上の「調べの回」の8)は調べで、集約・分け直し・消去は実行である。**方式(消去するか、非公開アーカイブへ移して旧URLを転送するか、転送しないか)は、元サイトでも回ごとに依頼者が選んでいて、決定の原文は確認できていない。このサイトでは、方式を勝手に決めない。依頼者が指示した方式で行い、指示が無ければ、方式を依頼者に聞く(不在の回は、その記事だけ保留にし、残りは進める)。**

1. **前提**: 「似ている」は、話題が同じではなく、同じ主要な悩み(悩み型でない記事は、同じ知りたいこと)に答えるかで決める。今のサイトにある記事どうしの比較だけで判断し、集約の履歴には頼らない。質の良し悪しはAIが決めない(依頼者が目視して決める)。
2. **集約するか、問いを分けるか**: 洗い出しで出たグループごとに、依頼者が目視して (a)集約(1本にする。残す1本=吸収先も依頼者が決める)か (b)問いを分ける(各記事の②を別の悩み・知りたいことにする。分けた問いも、悩み型は実在の声から出し、想像でずらさない)かを決める。決まるまで、そのグループは書き直しにも消去にも進まない。分けにくければ集約する。3本を3本に直して、重複の多いほとんど同じ記事にしない。
3. **吸収の決まり**: 後の回で、吸収先と同じ悩みの記事が見つかったら、書き直さず吸収先に集約する。吸収先に加えるのは、吸収される記事が答えていて吸収先がまだ答えていない分だけ(同じ分は足さない)。吸収先は、規則(11・30・31・35)で作り直す。URL・slug・date は変えず、updatedDate だけ実行直前に当日にする。吸収した本数は記事に残さない。
4. **取り込みの決まり(担当への指示に書く)**: 編集してよいのは吸収先の記事ファイル1本と自分の報告だけ(移動・削除・commit・push は親)。作業前に吸収先と吸収元の全文を読む。吸収先に同じ内容があれば取り込まない。出典は出典欄(frontmatter の sources)だけを扱い、出典を新しく探さない。**安全のための注意(怪しい勧誘の相談先・税務の確認先・収入の断定を避ける言い回し・個人差の注意)は集約で弱めない。** 減った注意を、報告に「前→後」の数で書く。既存の見出し(H2/H3)の文言は変えない(charts・accordions・imageBrief が見出し文で位置を指す)。吸収元の図・画像は持ち込まない(文章の節だけ)。吸収元を指す内部リンクは書かない(親が付け替える)。地の文が400字を超えて続かないようにする。一人称の体験談・伝聞表現・収入や成果の断定を書かない。検査(`verify-article.js`)の止める項目をPassにする。
5. **親の作業(担当の報告を受けて、組ごとに)**: 吸収元を指していた他記事の内部リンクを、吸収先へ付け替える(リンク先・案内の文言を吸収先の題に合わせる)。題を変えた記事を指すリンクの文言も新しい題に直す。吸収元の専用画像は、他の記事と共有されていないことを `git grep` で確かめてから消す。コード(`pages`・`lib`・`components`)に slug の直書きが無いかを `git grep` で確かめ、当たれば消去の前に依頼者へ報告する。消したあと、全記事から「実在しない `/posts/…`」を列挙して0件にする。公開待ちの記事のslugは、公開で日付が付け替わる。公開待ち同士のリンクは、リンク先が先に公開される順であることを確かめる。
6. **消去の方式ごとに手で直す場所**: 吸収元の記事ファイル(`公開済み/` または `公開待ち/`)を、依頼者が指示した方式で処理する(サイトのビルド〔`sync-content.js`〕は公開済みだけを読むので、公開済みから外せばサイトから消える)。サイトの検索・一覧・sitemap・関連記事は次のビルドで自動で消える。旧URLの転送の要否と方法は依頼者が決める(このサイトは `output: "export"` の完全静的エクスポートで、`vercel.json` は無い。転送を入れるなら、方法を依頼者に聞く)。作成中の作業フォルダは触らない(git の追跡外)。統合で記事として使われなくなる悩みは、`サイト運営/記事データ/作成中/` に記録して、次の記事作りの参考にする。
7. **本番の確認**: push の5分後に、トップ HTTP 200・sitemap の記事URL件数が消した本数だけ減っている・吸収先の記事ページ HTTP 200・消した記事のURLが開けない・サイト内検索と一覧に出ない、を確かめる。画面は親が自分で開いて見る。
8. **止めどころ(依頼者の確認が要る点)**: 集約か分けるかと吸収先の決定、質の評価の最終決定、旧URLの転送の要否、吸収先の題の変更(題の語は依頼者の決定が正)。

## 確認の方法(置き換えの前後・公開前)

- 置き換えの前後: 旧版の写しと、置き換える前の公開済みの md5 が一致すること。下書きと公開済みの title・date・導入が一致すること(置き換えの前後で、確定した下書きの md5 が同じことを表にしておく)。
- LF: 下書き・公開済みとも CR が 0 行、末尾に改行あり。
- 画像: `thumbnail` と本文の画像パスがすべて git に追跡されているか `git ls-files` で確かめる。
- 内部リンク: 本文と frontmatter のリンク先(`/posts/…`)が実在するかを、全記事から拾って確かめる(実在しないものを0件にする)。題を変えた記事を指すリンクの表示と案内の文が古くなっていないかも探す。公開待ち同士のリンクは、リンク先が先に公開される順であることを確かめる(逆だと、公開の間リンクが切れる)。内部リンクは必須ではない(`writer.md` の内部リンクの項)。外部リンクが本文にあれば記録する。
- HTMLコメント: `grep -rn "<!--" サイト運営/記事データ/公開済み/ サイト運営/記事データ/公開待ち/` で0件(画面には出ないが、ソースに出る運用メモを残さない)。
- 検査の道具: `verify-article.js`(止める項目のNoは直す。参考の項目は結果だけ書く)・`verify-rendered-layout.js --strict`(実測のレンダリング検査。図の重なり・はみ出し。0件でなければ pushしない)。判定の合否が変わる、または検査のスクリプトを直したときは、変更前後の挙動を報告の最初に書く。
- 本番: 上の手順の7。

## 失敗例と再発防止

| 失敗 | 再発防止 |
|---|---|
| 依頼者が新しい資料を見つけられない(古い目視用ファイルを開いた。報告がファイル名だけだった) | 報告はフルパス。目視用は新しい名前で出し、前のものは書き換えない |
| 報告で「ある」と書いたファイルが無かった | 報告の前に、ファイルの実在(パス・サイズ)を確かめる。返す前に output-crosscheck(`publisher.md` の「報告の型」) |
| 確認担当を1体起動し忘れた | 起動リストを指示に番号で書き、定義と実際の体数を判定に正直に書く |
| 検査のためにリポジトリを丸ごと複製して、大きな一時フォルダが残った | 複製しない(git worktree も使わない。`publisher.md`)。一時フォルダは検査の担当が、自分専用に作って消す |
| 古い版を見て作業した(同名ファイルに更新が重なった) | 変更前の写しは新しい名前で残す(`_第N回前`)。作業ファイルの先頭に「最終更新」「変更点」を書く |
| 担当が、規則・検査・サイトのコードの写しを勝手に直した | 共通の指示の禁止節に「規則本文・検査・サイトのコード・他の記事に触れない」を必ず書く |
| 作業の成果物を `docs/` に置いた | 作成中の回のフォルダへ |
| 記事を変えたのに、公開の対象に入れなかった(リンク表示だけ直した記事を含む) | 公開済みのファイルを変えた記事は、すべて同じ commit に入れる(`publisher.md`) |
