# Web記事執筆スキル(ライター)

## frontmatter
記事Markdownの冒頭に以下を必ず含める。
```yaml
---
title: "SEOキーワードを含むタイトル"
description: "検索結果に表示される120字程度の要約"
category: "対象ジャンルのカテゴリ(例: 制作時に指定)"
tags: ["キーワード1", "キーワード2"]
affiliateLinks:
  - label: "紹介する商品・サービス名"
    url: "アフィリエイトリンクURL"
---
```
提携先が未整備の場合は `affiliateLinks` 自体を省略する(空配列やプレースホルダー文言を残さない)。`label`/`url`以外のキー名(`name`等)を使うと `/compare` ページのビルド時に値が`undefined`になりビルドエラーになるため、キー名は必ずこの2つで統一する。

## トーン: 案内役として書く
専門的な内容でも、論文・教科書・説明書のような硬い解説文にしない。読者に一方的に講義する専門家ではなく、隣で分かりやすく教えてくれる案内役のトーンで書く。
- 専門用語は初登場時にだけ「〇〇(簡単な言い換え)」のように一言添える。2回目以降は繰り返し説明しない
- 専門用語を連続させない。難しい言葉が続く場合は、間に平易な言い換えや具体例を挟んで呼吸を作る
- 一文を長くしすぎない。読点が3つ以上続く一文は、意味の区切りで分割する
- 「〜な経験、ありませんか」「〜って気になりますよね」のような読者への語りかけを、見出し1〜2個につき1回程度の頻度で適度に入れる(入れすぎると軽薄になるので詰め込まない)
- 親しみやすさを保ちつつ幼稚にはしない。タメ口だけで押し通す・体言止めを連発する等の崩しすぎた文体は避ける

## 執筆前チェック: 記事重複防止
書き始める前に、既存記事と検索意図が重複していないか確認する。
- `記事データ\確定稿\` の既存ファイル、および公開済み記事(サイト本体の記事データ)に同じ検索意図の記事がないか確認する
- 似たテーマが既にある場合、対象読者・検索意図・解決する悩みのいずれかを明確に変える(例: 初心者向けの基礎記事と経験者向けの実践記事を分ける)
- タイトル・見出し構成を既存記事と似せすぎない。同じ説明を別記事でそのまま繰り返さない

## 執筆の型
1. リード文: 検索意図に即答する結論・要点を先に示す。**分析者が特定した「競合記事の弱点・不足点」を踏まえ、その記事にしかない切り口や情報を早い段階で示す。競合と同じ一般論の言い換えで終わらせない**
2. 見出し(H2/H3): 想定検索キーワードを含む見出しで本論を構成する
3. 具体的な内容: データや理由を"会話的"に触れる(数値の羅列にしない)。丸数字の箇条書きを多用しすぎない。**ただし核となる具体的事実(数字・固有の条件・期間など)は各見出しに最低1つは残す。抽象論だけで終わらせない**
4. アフィリエイトリンク配置: 文脈に沿って自然に商品・サービスを紹介する箇所に配置し、広告表記(PR/広告等)を明記する
5. まとめ: 記事の要点と、次の行動(比較ページ・ランキングページ・商品ページ等への導線)を示す。**テンプレ的な汎用フレーズで終わらせず、本文の具体的内容に紐づいた結論にする**

## 段落の長さ
1段落に3文以上を詰め込まない(目安2〜3文、長くても4文まで)。話題や視点が変わる箇所(「そもそもの原因」→「対策」、「一般論」→「私の体験」など)では必ず段落(空行)を分ける。1文が長い場合も、読点の多い一文をだらだら続けず、意味の区切りで文自体を分割する。読者がスマホの狭い画面で読む前提で、圧迫感のある「文字の壁」を作らない。

## AI感を避けるルール
- 「〜と言われています」「〜というデータも」を1記事内で2回以上使わない
- 一人称・実体験ベースの語り口を優先する(「〜って気づいた」「〜してみようと思う」)
- 断定的な効果表現は避けつつ、ヘッジ表現(個人差があります等)を連発しない。1箇所にまとめる
- 数値データを羅列せず、必要な範囲に絞って触れる

## 「読まれる・上位表示される」ための必須チェック
- ヘッジ表現で具体性を薄めすぎていないか。法務上必要な最低限のヘッジは残しつつ、それ以外まで曖昧にして当たり障りのない記事にしない
- 分析者が特定した競合記事の弱点を、自社記事で実際に埋められているか
- 読み終えたときに「この記事は他と違って役に立った」と思わせる一点があるか。なければ書き直す

## 内部リンク設計
読者が次に知りたい情報へ自然に進めるよう、関連性の高い記事・カテゴリページへのリンクを本文中に含める。
- 同じカテゴリ内の関連性の高い記事へリンクする
- 初心者向け記事からは、より詳しい記事・比較記事へ誘導する
- 詳細記事・レビュー記事からは、基礎を説明した記事へ戻れるようにする
- SEO目的だけでなく読者の理解を深める導線として設計する(リンク先が存在しない場合は無理にリンクを作らない)

## 商品・サービス紹介の書き方
単なる広告記事にならないよう、読者が納得して選べる情報提供を目的とする。
- メリットだけでなく注意点・向かない人も書く
- ランキング形式の場合は、何を基準に順位付けしたか(価格/サポート体制/実績など)を本文中で明示する
- 「絶対」「誰でも」等の断定的な購入・登録誘導は避け、読者が自分の状況に照らして判断できる情報を提示する

## 本文の装飾記法
サイト側のMarkdown処理(remark-gfm対応済み)で以下が使える。多用しすぎず、本当に強調したい1〜2箇所に絞る。
- `==強調したい語句==` → 黄色マーカーのハイライト
- `++強調したい語句++` → ブランドカラーの下線
- `**太字**` → 標準の強調(すでにブランドカラーで装飾済み)
- `~~誤り・古い情報~~` → 打ち消し線(訂正・古い情報の明示に)
- `^^気づき・感情が変わる一文^^` → 文字を大きく・青色にして目立たせる強調(「実は思い込みだった」「これは驚いた」のように、読者の認識が変わる/感情が動く一文にだけ使う。地の文の説明にはつけない)。絵文字(💦😳など)は装飾記法とは別に、地の文にそのまま書いてよい
- `%%出典の信頼性・注意点の一言注記%%` → やや小さめ・控えめな色で表示(0.88em/グレー系)。「なお、この見解は企業運営のコラム記事によるもので〜」のような、本文の主張ではなく出典の性質・留意点を添える一文にのみ使う。**景品表示法の打消し表示規制に配慮し、効果効能等の強調表示を打ち消す注記をこの記法で目立たなくする目的では使わない**(読めなくなるほど小さく・薄くしてはいけない)
- Markdownの表(`| 見出し | 見出し |` 形式)・番号なしリストがそのまま使える(表は比較・まとめ情報がある記事でのみ使用し、無理に入れない)

強調記法は1記事に対して合計3〜4箇所程度を上限とし、全部乗せにしない(ハイライトだらけの記事はかえって読みにくい)。

## ラベル表記(💡ポイント/⚠注意/✅まとめ)
要点整理・注意喚起・まとめなど、目立たせたい塊には絵文字1つ+短いラベルの行を見出し代わりに使ってよい。
- 「💡ポイント」「⚠注意」「✅まとめ」「☑チェック項目」のように、絵文字1個+ラベルの組み合わせで統一する。絵文字を複数並べる装飾(例: 「✨💡🌟おすすめポイント🌟💡✨」)はしない
- 1記事内で同じ用途には同じラベル表記を使い、揺らさない(「ポイント」と「Point」を混在させない等)
- ラベル行だけで終わらせず、直後に内容のある文章を続ける(例: 「💡ポイント」の次に「○○を選ぶ際は、価格だけでなく成分も確認しましょう。」)

## マスコットキャラクター登場ルール
マスコットは読者理解を助ける案内役として使う。**本文全体をキャラクター口調にするのは禁止**。基本の文章は通常の記事調のまま、要所にだけ自然に登場させる。
- **記事冒頭(リード文の直前)への画像付きマスコット登場は必須。省略しない。** 対象カテゴリでは`[mascot-image]`(または`[mascot-image: せりふ]`)を、対象カテゴリのマスコットが未登録のカテゴリではMarkdown引用(blockquote)での名前+せりふ表示を、本文冒頭に必ず入れる
- それ以外に登場させてよい箇所の目安: 難しい内容・専門用語の補足/表やデータの読み取り方の案内/注意事項/まとめ。**冒頭分を含めて必要な2〜3箇所程度に絞り、全部に詰め込まない**
- 対象カテゴリ(`サイト本体\lib\categoryMascot.js`の`CATEGORY_MASCOTS`参照)では、frontmatterの`mascotComment`によりサイト側で本文中盤(H2見出しの直前)へ画像付き吹き出しが自動挿入される。これで1箇所分をカバーできる
- それ以外の箇所(冒頭・まとめ等)で画像付き吹き出しを出したい場合は、対象カテゴリの記事に限り、本文の単独行に `[mascot-image]` と書く。その段落がfrontmatterの`mascotComment`を使った画像付き吹き出しに自動変換される。自動挿入(本文中盤)と文言を分けたい場合は `[mascot-image: 〇〇は最初にここを確認しておくと安心だよ。]` のようにコロン以降へその場のせりふを直接書ける
  ```
  [mascot-image: 〇〇は最初にここを確認しておくと安心だよ。]
  ```
- 対象カテゴリのマスコットが未登録の場合、または画像なしで軽く触れたいだけの場合は、Markdownの引用(blockquote)で名前+せりふのテキストのみ表示する方法も使える。
  ```
  > **{マスコット名}**: 「〇〇は最初にここを確認しておくと安心だよ。」
  ```
- マスコット名は担当カテゴリのキャラクター名(categoryMascot.js参照)に統一する
- せりふは40〜70字程度、「〜だよ」「〜してみてね」のような親しみやすい口調。本文の要約ではなく、視点の切り替えや一言アドバイスとして書く
- 自動挿入分(mascotComment)と本文中への手書き分を合わせて、1記事あたり合計2〜4箇所を上限とする

## サムネイル画像
frontmatterの`thumbnail`(例: `/images/articles/YYYY-MM-DD_テーマ.webp`)は、ホームページ・カテゴリ・検索・ランキングの記事カードと記事ページ上部のヒーロー画像、他記事ページの「関連記事」カード、SNSシェア時のOGP画像に使われる。ライターが画像を用意する必要はない(サイト側で別途生成・設置する運用)。確定稿を渡す際、まだ画像がない場合はfrontmatterに`thumbnail`を書かなくてよい(未設定の記事は関連記事欄で本アイコンの代替表示になる)。

## 表・グラフを使うかどうかの判断基準
情報量を増やすためではなく、読者の理解を助けるために使う。優先順位の目安は次の通り。
1. 複数の商品・サービスの比較、メリット/デメリットの整理、料金・スペック比較 → Markdownの表(`| 項目 | 特徴 | おすすめの人 | 注意点 |`のように、読者が比較・判断しやすい列を設定する。単なる情報の羅列にしない)
2. 市場規模・年代別傾向・割合の推移など数値の変化 → `charts`のグラフ(下記参照)
3. 手順や流れの整理 → 番号付きリストまたは表
4. 文章だけで十分理解できる内容 → 無理に表・グラフを追加しない

表・グラフを配置する場合は、貼るだけで終わらせず前後の文章で「何を表しているか」「読者は何を読み取ればよいか」を必ず補足する。重要な情報を画像だけに含めず、Markdown表や本文の文章でも同じ内容が伝わるようにする(検索エンジン・スクリーンリーダー対応)。

## 統計データ・グラフの提案
執筆中に信頼できる一次情報(政府統計・大手企業や調査会社の公表調査など)で、記事の主張を裏付ける具体的な数値が見つかった場合、frontmatterに以下の形式で`charts`を提案してよい(採用可否・最終調整は編集長が行う)。`type`は用途に応じて使い分ける。

- `stat`: 単一の割合・人数など、比較対象がない1つの数値を大きく見せる
- (typeを省略): 複数カテゴリの量を比較する棒グラフ
- `pie` または `donut`: 内訳・構成比(合計100%になる項目)を円グラフで見せる。5項目まで(6項目以上は自動的に上位4件+「その他」にまとめられる)
- `prosCons`: メリット/デメリットの比較を色分けした2カラムで見せる

```yaml
charts:
  - afterHeading: "この見出しの直後に挿入(本文の見出しテキストと完全一致させる)"
    type: "stat"   # 単一の数値
    value: "82.7"
    unit: "%"
    label: "何の割合かを説明する短い文"
    source: "調査主体名「調査タイトル」(実施時期・n数があれば併記)"
    sourceUrl: "出典URL"
  - afterHeading: "別の見出し"
    # 棒グラフ(typeを省略)。項目間の量を比較したい場合
    title: "グラフのタイトル"
    data: [{label: "男性", value: 38.5}, {label: "女性", value: 43.6}]
    unit: "%"
    source: "..."
    sourceUrl: "..."
  - afterHeading: "内訳を説明する見出し"
    type: "pie"    # 内訳・構成比(合計約100%になるデータ)
    title: "グラフのタイトル"
    unit: "%"
    data: [{label: "原因A", value: 45}, {label: "原因B", value: 30}, {label: "原因C", value: 25}]
    source: "..."
    sourceUrl: "..."
  - afterHeading: "比較したい見出し"
    type: "prosCons"
    title: "メリット・デメリット比較のタイトル(任意)"
    pros: ["メリット1", "メリット2"]
    cons: ["デメリット1", "デメリット2"]
    # prosConsは出典データではなく本文の整理なのでsource/sourceUrlは不要
```
- 出典は必ず一次情報(官公庁・調査実施企業の公式発表)のURLを明記する。まとめサイトや又聞き情報のみを出典にしない(`prosCons`は出典不要)
- 数値は概数(「約80%」等)であればそのまま概数と明記し、正確な数値であるかのように断定しない
- 1記事に詰め込みすぎず、本文の主張と直結する統計・比較に絞る(無理に全記事へ追加する必要はない)

## 記事全体の設計イメージ
上記の各ルールを踏まえた基本構成は以下の流れになる(すべての要素が必須ではなく、記事の性質に応じて取捨選択する)。

```
タイトル(SEOキーワードを含む)
↓
冒頭のマスコットのひとこと(必須。マスコットキャラクター登場ルール参照)
↓
導入文(読者の悩み・検索意図への共感 → 結論の先出し)
↓
「この記事でわかること」(💡ポイントのラベルを使った箇条書き。任意)
↓
本文(見出し・具体例。比較や数値変化があれば表/グラフ、判断基準を明示)
  ├ 本文中盤にサイト自動挿入のマスコットコメント(mascotComment)
  └ 難しい内容の補足・注意事項は⚠注意ラベルや手書きのマスコットせりふで整理
↓
重要ポイント整理(✅まとめラベル等)
↓
まとめ(要点+次に取るべき行動を促す)
↓
まとめ後のマスコットコメント(任意)
```

## 保存ルール
- 下書き段階は `サイト運営\実務\ライター\YYYY-MM-DD_テーマ_v1.md` のようにバージョンを明記して保存する
- 確定稿は編集長がfrontmatter込みで `記事データ\確定稿\YYYY-MM-DD_テーマ.md` に保存する
