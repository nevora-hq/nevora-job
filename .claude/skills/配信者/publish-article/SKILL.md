# 記事公開スキル(配信者)

> **【ルール本体は`.claude/agents/publisher.md`が正】** 詳細な手順・判定基準・出力フォーマットは`.claude/agents/publisher.md`を参照すること。**このファイルとpublisher.mdの記述が食い違った場合は、常にpublisher.mdを正としてこのファイル側を修正する。**

## 記事が公開される経路(このスキルは新規公開を行わない)

記事の状態は 作成中 → 公開待ち → 公開済み の3つで、置き場の決まりは `.claude/skills/run-article-production/SKILL.md` の「記事の状態と置き場」が正。新規記事は、最後の判定(`scripts/verify-article.js` の全ブロッキング項目Pass を含む)を通って、公開する版の1ファイルが `記事データ\公開待ち\` に置かれ、`npm run queue` で公開予定日時が割り当てられ、GitHub Actions(`.github\workflows\publish-queue.yml`)が30分おきに `scripts\queue-release.js` を動かして、公開時刻の到来した記事を `記事データ\公開済み\` へ移してcommit・pushする。pushでVercelが自動デプロイし、そこで初めてサイト・sitemapに出る。

## 公開の決まり(2026-10-12 依頼者の決定。主となる文はここ。ほかのファイルはこの文に合わせる)

「記事の状態と置き場」の決まり(作成中 → 公開待ち → 公開済み)は変えない。公開のしかたは、依頼者の指定の有無で分ける。

**ア. 依頼者が「すぐ公開」と指定した記事(1本でも複数でも)**
- 公開の時刻(`publishAt`)を今の時刻以前にして、公開待ちに置く。
- commit して push したあと、公開の処理を手動で実行する(GitHub Actions の `publish-queue` を手動で実行する。または手元で `TZ=Asia/Tokyo node scripts\queue-release.js` を実行し、移ったファイルを名前を指定して commit、push する)。
- 本番でその記事が表示されることを確かめて、報告する。

**イ. それ以外の記事(指定が無い。複数の記事をまとめて作る場合を含む)**
- 予約投稿にする。公開の時刻は、`npm run queue`(`scripts\queue-schedule.js`)で割り振る。担当が手で決めない。
- 公開待ちに置いて、commit して push する。そこで終わる。push する前に、公開待ちに置いた記事すべてに、公開の時刻(`publishAt`)が入っていることを確かめる。入っていない記事は、公開されないまま残る。
- 公開は自動処理に任せる。公開されるのを待たない。手動でも実行しない。
- 報告に、記事ごとの予約した時刻と、「公開後の確認は未実施」と書く。

手順の細部は publisher.md の「公開の決まり」が正(食い違ったら publisher.md を正とする)。作業フォルダから、ファイル名を指定して commit・push し、別の作業用の写し(worktree)は使わない。

このスキルの担当は、(a) 既に公開済みの記事に加えられた修正をサイトへ反映すること、(b) 公開後のPinterest追記・ピン画像作成 の2つである。新規記事の公開は、依頼者が「すぐ公開」と指定した記事に限り、上の「公開の決まり」のアのとおり、このファイルの公開の手順を実行する者(サブエージェントを束ねる側)が行う(publisher.md の例外)。指定が無い記事は、イのとおり予約投稿にして push で終える。

## 公開ゲートと台帳は、このサイトでは使わない(2026-10-12)

`scripts/autonomy/publish-gate.js`・台帳(`publish-ledger.json`)は、このサイトのコードに無い。サイトのビルドも公開キューも台帳を見ないので、`publishable` を確かめる手順は使わない。公開前の確認は、`node scripts/verify-article.js <記事>`(全ブロッキング項目Pass)・手元のビルド・スマホ幅とパソコン幅の目視で行う(詳細は publisher.md)。

## サイトのコードに仕組みが入るまでの手順(詳細はpublisher.md参照)

公開する版の作り方(出典の印は原稿に残してよい〔コードが画面に出さない〕・`afterParagraph` と `imageBrief` の取り外し・`sectionAlternate: false`・画像の入れ方・手元ビルドと幅の確認・作業フォルダから、ファイル名を指定した commit・push〔2026-10-11 依頼者の決定〕。公開のしかたは「公開の決まり」のア・イ)と、判定を手で行うときのやり方は、publisher.md の「サイトのコードに仕組みが入るまでの手順」が正。コードに仕組みが入ったら、その手順は使わない。push の前に、`%%出典:…%%` の印が画面に出ておらず本文の段落に「出典:」の文字が出ていないこと(2026-10-11 依頼者の決定。出典は記事末の「出典」欄。図表の下の「出典:」は対象外で残す)と、同じ語尾が3文以上続く箇所が無いこと(2026-10-11 依頼者の指摘)も確かめる。

## 反映の前提(ゲート、詳細はpublisher.md参照)

`記事データ\公開済み\`配下の記事をcommit・pushする前に、`node scripts/verify-article.js "<対象記事の絶対パス>"` を必ず実行する。**目視での「合格しているはず」という推測でゲートを通さない。**

- 実行そのものは必須で、`overall=No`の記事は公開せず、直してから公開する(publisher.mdの「公開前の必須確認(ゲート)」節参照)。信頼性系ブロッキング違反(item10/11/12等)が公開済みの記事に見つかった場合は即時修正が原則、修正に時間を要する場合の非公開化は**必ずユーザー決裁を経る**(`docs/CONTRIBUTING.md` 26節(b))
- 実行結果のJSONは `docs/pipeline/verify/{slug}_{実行日 YYYY-MM-DD}.json` に保存する

## 反映の流れ(概要)

1. `git status` で `サイト運営\記事データ\公開済み\` 配下に未コミットの変更が無いか確認する
2. 変更があれば、内容(記事タイトル・変更概要)を報告に書いたうえで、確認を待たずに該当ファイルを明示的に指定して`git add`→`git commit`(記事タイトルを含むメッセージ)
3. `git push`の前に、依頼者の確認は取らない(2026-10-03 依頼者の決定)。公開の手順(最後の関門の表・verify-article.js の全ブロッキング項目Pass・手元のビルド)を満たしたら push する
4. push後、Vercel側の自動デプロイ完了を確認する(反映確認は最低5分待つ、`CLAUDE.md`のデプロイ運用ルール参照)

## サイト未実装の場合

`サイト運営\サイト本体\`にNext.jsプロジェクトがまだ存在しない場合は、作業を中断し、`site-engineer`による最低限の実装を先に依頼するようユーザーに案内する。

## エラー時

git操作やビルドが失敗した場合、エラーメッセージをそのまま報告し、憶測で原因を断定しない。原因調査が必要な場合はincident-responderへの依頼を提案する。先行 commit で弾かれた場合の取り込み方は CLAUDE.md のデプロイ運用ルールのとおりにし、行ったことを報告する。
